# 服务端工程规范

## 这份文档是什么

这份文档规定 C# 服务端代码应该怎样生成和维护。

初学者可以这样理解：服务端是 App 背后的云端后台，负责账号、情侣绑定、授权、聊天、轨迹、设备状态、AI 分析和推送通知。服务端必须稳定、可审计、可排查，并且不能泄露隐私。

## 技术固定选择

服务端首版使用：

- C#。
- .NET 10。
- ASP.NET Core Minimal APIs。
- PostgreSQL、PostGIS、Redis、RabbitMQ + MassTransit。
- `Microsoft.Extensions.AI + IChatClient`。
- OpenTelemetry。

首版不上 MAF，不使用 `Microsoft.Agents.AI`。

## 服务边界

服务端代码必须按业务边界组织：

- 账号服务只管身份。
- 情侣服务只管绑定关系。
- 授权服务只管权限和授权版本。
- 定位服务只管位置点和轨迹。
- 设备状态服务只管电量、充电、Wi-Fi、用机、App 打开、通话状态摘要。
- 聊天服务只管绑定情侣之间的消息。
- RTC 网关只管音视频 token 和回调。
- AI 隐私服务只管受控 AI 分析。
- 通知网关只管厂商推送。
- 审计服务只管敏感操作元数据。

服务之间不能随意读取彼此数据库。需要跨服务协作时，优先通过接口或事件。

## API 规则

移动端接口使用 HTTPS JSON。

每个接口必须做到：

- 默认鉴权。
- 情侣数据必须校验绑定关系。
- 敏感写入必须校验双方授权。
- 返回稳定错误码。
- 返回面向用户的中文错误解释。
- 写操作必须可审计。

接口代码要薄。路由层只负责接收请求、调用服务、返回结果，核心业务规则放在服务或领域类库里。

## 日志规则

服务端统一使用 `ILogger` 结构化日志。

推荐字段：

- `service_name`：服务名。
- `operation`：操作名。
- `correlation_id`：一次用户操作的关联 ID。
- `trace_id`：链路追踪 ID。
- `span_id`：当前步骤 ID。
- `result`：成功或失败。
- `error_code`：稳定错误码。
- `duration_ms`：耗时。

禁止记录：

- 聊天原文。
- 完整经纬度。
- Wi-Fi 名称。
- 手机号。
- 验证码。
- token。
- prompt 原文。
- 模型输入快照。

如果需要记录用户或情侣标识，只能记录哈希后的 `user_id_hash`、`couple_id_hash`。

## OpenTelemetry 规则

服务端必须接入 OpenTelemetry 的三类信号：

- Logs：结构化日志。
- Traces：链路追踪，说明一次请求经过了哪些服务和步骤。
- Metrics：指标，例如请求量、失败率、延迟。

新增 ASP.NET Core 服务时必须调用共享入口：

```csharp
builder.Services.AddAiAppObservability(options =>
{
    options.ServiceName = "AIAPP.IdentityService";
});
```

应用启动时必须启用关联 ID 中间件：

```csharp
app.UseAiAppCorrelationId();
```

服务还必须提供健康检查：

```csharp
app.MapHealthChecks("/healthz");
```

## AI 调用规则

业务代码不得直接调用模型 SDK。

所有涉及情侣聊天、定位轨迹、用机状态的 AI 分析，必须经过 `AiPrivacyGateway`。

AI 分析链路必须能追踪：

- 授权校验。
- 最小必要数据拉取。
- 模型调用。
- 结果保存。
- 审计记录。

Trace 里只能记录元数据，不能记录 prompt 或隐私原文。

## 错误处理规则

错误处理要让客户端能显示清楚的中文提示。

例如：

- 未登录：提示重新登录。
- 未绑定情侣：提示先完成绑定。
- 授权缺失：提示双方需要先授权。
- 模型超时：提示 AI 暂时不可用。
- 推送失败：服务端重试，客户端下次打开时同步。

不能把异常堆栈直接返回给客户端。

## 测试规则

服务端至少要覆盖：

- 解绑后访问情侣数据失败。
- 任一方撤回授权后敏感写入失败。
- AI 未授权时分析失败。
- 审计日志不包含隐私原文。
- OpenTelemetry 注册缺失时门禁失败。
- 推送失败可重试。
